## 1. 已修复（12 项）

### 1.1 [高] `/api/policy-qa/ask` 答案路径仍在隐藏检索降级

- **位置**：`app/scenarios/policy_qa/schemas.py`（`QAResponse`）、`app/scenarios/policy_qa/orchestrator.py`
- **现象**：`QAResponse` 只有 `answer / confidence / has_evidence`，**没有降级字段**。降级只被写进 LLM 的系统提示词，从不进入响应体。
- **原因**：同日早先只修了 MCP 的 `search_policy` 工具出口，**没修合成答案这条出口** —— 又一次"约定只在部分地方落实"。
- **影响**：所有走 `/api/policy-qa/ask` 的调用方（含前端）在排序退化成纯关键词时，会收到 `answer` + 高 `confidence`，与事故原文"接口照常返回 FOUND 和一段自信的摘要"完全一致。
- **修复**：`QAResponse` 增加 `retrieval_degraded: list[str]` 与 `retrieval_note: str | None`；`orchestrator` 在**三处**返回点回填（主路径、间接注入拦截、流式 `done` 事件）。
- **验证**：新增 2 个测试，分别锁非流式响应体与流式 `done` 事件。

### 1.2 [高] `documents` 去重索引不含 `tenant_id`（跨租户冲突）

- **位置**：`app/data/migrations/versions/003_document_integrity.py:21-27`、`app/data/models/knowledge_base.py:43-50`
- **现象**：唯一索引 `uq_documents_kb_content_sha256_nonempty` 建在 `(kb_id, content_sha256)` 上，**没有 `tenant_id`**。
- **原因**：唯一约束是全局的，而数据是租户隔离的 —— 两者作用域不一致。
- **影响**：两个租户在同一个 `kb_id` 下上传相同内容，**后上传的那个**会收到 `IntegrityError`；而 RLS 把冲突行藏了起来，所以从它的视角这个报错毫无道理。**先上传的租户完全不受影响 → 单租户测试永远发现不了。**
- **修复**：迁移 `044_documents_tenant_dedup` 改为 `(tenant_id, kb_id, content_sha256)`，模型同步。注意方向：加 `tenant_id` 让约束**更宽松**，不可能在既有数据上失败，无需回填。
- **验证**：已在活库执行 `alembic upgrade head`，`pg_indexes` 确认索引已变更。

### 1.3 [高] `PUBLIC_BASE_URL` 空 `base_url` 产生误导性错误 → dense 腿静默死亡

- **位置**：`app/rag/embedding/__init__.py:67`（`get_embedder`）
- **现象**：`EMBEDDING_BASE_URL` 为空时 `AsyncOpenAI(base_url="")` 在**请求时**抛 `APIConnectionError("Connection error.")`。这条错误被 `Retriever._hybrid` 的 `return_exceptions=True` 吞掉，dense 腿静默消失。
- **原因**：`get_embedder()` 只校验 api_key，不校验 base_url；且 dev 环境下 `validate_environment` 的 embedding 校验被 `if app_env in {staging, production}` 跳过。
- **影响**：**这正是本日事故的真实机制**。模糊的连接错误比明确的配置错误难查得多 —— 只能从"检索结果为什么不对"逆推回"少了一个环境变量"。
- **修复**：`base_url` 为空时直接抛指名道姓的 `RuntimeError`（含示例取值与后果说明）。
- **验证**：实测确认异常类型与文案。

> **附带更正**：本仓库另一份文档早先写的是"`AsyncOpenAI` 静默回落到 `api.openai.com` 并 401"。**那句是错的**（未经验证的推断）。实测 `c.base_url` 为空串、抛 `APIConnectionError`，不存在 401。已在 `docs/ops/2026-09-16-…md` 中原位更正并说明为什么这个区别会影响排查方向。

### 1.4 [中] `oauth_issuer` 默认值与 `app_port` / `public_base_url` 自相矛盾

- **位置**：`app/config/settings.py:108`（`app_port=8000`）、`:147`、`:171`、`_DEFAULT_OAUTH_ISSUER_ORIGIN`
- **现象**：`app_port` 与 `public_base_url` 默认都是 `8000`，而 `_DEFAULT_OAUTH_ISSUER_ORIGIN` 是 `8001`。
- **原因**：三者指的是同一个 origin（单端口部署下 AS 挂在 app 自己身上），任何一项单独漂移都会让 iss/aud 比对失败，而失败只发生在客户端、服务端只留一句 `malformed`。这个常量是本日早先引入的，当时没与另两项对齐。
- **影响**：单端口部署下 issuer 指向一个没人监听的端口，外部令牌全量被拒。
- **修复**：改为 `http://localhost:8000`，并加注释说明三者必须同源。
- **验证**：**这次修改让 2 个测试失败** —— 它们硬编码了旧默认值。修法不是改数字，而是让测试从 `settings` **导入**该常量，消除这处重复（否则还会再漂）。

### 1.5 [中] README 让 Compose 用户把 MCP 指向 `8001`，与 audience 要求不符

- **位置**：`README.md:165`、对照 `docker-compose.yml:85` 与 `web/nginx.conf:14-25`
- **现象**：README「个人本机自托管（Docker Compose）」一行的 MCP 地址写 `http://localhost:8001/mcp`，而 compose 的 `PUBLIC_BASE_URL` 是 `http://localhost:3001`，nginx 在 3001 上代理 `/mcp`。
- **原因**：8001 是 app 容器的宿主映射口（`8001:8000`），不是对外 origin。
- **影响**：照 README 配外部 Agent 会申请 `aud=http://localhost:8001/mcp`，而 RS 期望 `http://localhost:3001/mcp` → **aud 逐字节不符 → 所有令牌 malformed**，与本次事故同一形态。这是"文档写错会精确复现一次事故"的例子。
- **修复**：README 改为 `http://localhost:3001/mcp`。

### 1.6 [中] `env.docker.example` 的 `PUBLIC_BASE_URL` 与 compose 冲突

- **位置**：`env.docker.example:84`
- **现象**：模板值 `8001`，compose `environment` 里是 `3001`；`environment` 优先于 `env_file`，所以模板值被静默覆盖。
- **影响**：改模板以为改了配置，实际没生效。原注释虽已提示"compose overrides these"，但取值本身自相矛盾仍会造成误判。
- **修复**：对齐为 `3001`，并在注释里写清"nginx 是入口、8000 只是容器内部监听口"。

### 1.7 [低] mypy 类型错误 2 处（**本日早先修复引入的回归**）

- **位置**：`app/scenarios/policy_qa/orchestrator.py:195, 373`

### 1.9 [低] 迁移 revision id 超过 32 字符会导致迁移失败

## 2. 核验后驳回（1 项）

### 2.1 ~~RLS 策略引用从未设置的 `app.current_tenant_id`~~ —— **假阳性**

- **审计员结论**：`007/008/009/010/011` 五个迁移建的 RLS 策略用的是
  `current_setting('app.current_tenant_id', true)`，而全仓只设置 `app.tenant_id`；
  这 5 张表又被 `014_force_tenant_rls` FORCE，因此"所有查询 0 行、写入被拒"，
  置信度标注为**"确认"**。
- **我的核验**：
  1. 字符串层面属实 —— `app.current_tenant_id` 确实只出现在那 5 个文件里；
  2. 但**存在一个后续修复迁移**：`012_object_acl_security.py:76-90` 的 `_replace_rls`
     循环**恰好覆盖这 12 张表**（含全部 5 张），用正确的 `app.tenant_id` 重建了策略，
     并补上了 `WITH CHECK`；
  3. **活库实证**（`pg_policies` + `pg_class`，当前 head `044`）：
     10 张目标表 `relrowsecurity=true`、`relforcerowsecurity=true`，
     而**实际策略全部是 `app.tenant_id`** —— 正确。
- **判定**：**不存在活跃缺陷。** 错误只存在于 007–011 的历史 DDL，012 已修正；
  按顺序跑迁移的新库最终状态也是正确的。
- **为什么会误判**：只做了字符串搜索，没有检查"后来是否有人修过"。
  **在一个有 44 个迁移的仓库里，"某处写法不对"与"系统行为不对"是两件事。**
- **残留价值**：值得留一句 —— 这 5 个历史迁移容易在下次搜索时再次误导人（我自己也差点被带走）。
