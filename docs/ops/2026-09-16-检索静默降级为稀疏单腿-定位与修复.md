# 2026-09-16 检索静默降级为稀疏单腿：定位与修复

**一句话**：`search_policy` 对"公司的年假是怎么规定的？"给出的**第一名是一条酒店工程部的
技能考核表**。答案其实早就在库里 —— 真正坏掉的是检索，而它坏得非常安静：接口照常回
`outcome: FOUND`，摘要照常写得像模像样。

---

## 1. 现象

真实 MCP 客户端（`eval-runner` 租户，`kb=policy_kb`）调用 `search_policy`：

| query | 返回的 top-1 | 应该是什么 |
|---|---|---|
| 公司的年假是怎么规定的？ | `11_酒店工程部员工转正、晋级技能考核表.docx / 总则` | 国务院令第514号《职工带薪年休假条例》 |
| 离职时未休年假怎么折算？ | `01_用友_HR工具书…pdf / 第十二条`（保密协议条款） | 人社部令第1号《实施办法》第十二条（折算公式） |

两条 query 的正确答案在库里都存在（`09_…条例.txt` / `10_…实施办法.txt` 已入库），
只是**排不上来**。

## 2. 为什么不能只看"能不能查到"

同一个 `Retriever().retrieve(...)`，在**进程内直连**调用时 top-1 是正确的国务院条例
（`dense` rank 0，`ds=0.7045`），经 **MCP 服务**调用时却变成 sparse rank 0 的考核表。
同一份代码、同一个 query —— 差别只可能在**运行中的那个进程**。

用 `top_k=5` 直连复跑三遍结果是稳定的，所以这不是"同分随机"能解释的。
真正把方向纠正过来的一步是去看**服务自己的健康端点**：

```bash
curl -sS http://127.0.0.1:8001/api/ready
# {"status":"degraded","optional_unavailable":["embedding"],
#  "checks":{...,"milvus":"ok","embedding":"unavailable","llm":"ok"}}
```

`milvus: ok` 但 `embedding: unavailable`。向量库是好的，**通向它的那条腿断了**。

## 3. 根因

`app/rag/retrieval/retriever.py::_hybrid` 用
`asyncio.gather(self._dense(...), self._sparse(...), return_exceptions=True)`：
dense 腿抛异常时被**吞掉**，只剩 sparse 腿参与 RRF 融合。

于是"稠密语义检索"整条腿消失，排序退化成**纯关键词匹配**：

- `09_国务院…条例` 靠语义相似（`ds=0.70`）才排第一，sparse 腿里它并不占优；
- `11_酒店考核表 总则` 因为字面命中"年""假"等高频词，sparse rank 0（`ss=26.8`）
  —— 在没有 dense 制衡时就直接坐上了第一。

**为什么 dense 腿会断**：`get_embedder()` 走 OpenAI 兼容端点，`.env` 缺
`EMBEDDING_BASE_URL` 时 `base_url` 是空串，于是 `AsyncOpenAI(base_url="")` 在**请求时**
抛 `APIConnectionError("Connection error.")` → `_dense` 抛异常 → 被
`return_exceptions=True` 吞掉。

> **更正（同日复核）**：本文早先写的是"`AsyncOpenAI` 会静默回落到 `api.openai.com`
> 并 401"。**那句话是错的**，属未经验证的推断。实测（`AsyncOpenAI(base_url="")` 后发起
> 一次 embed 调用）：`c.base_url` 为空串，抛出的异常是 `APIConnectionError`，
> 不是任何带状态码的 401。
>
> 结论不变（缺配置 → dense 腿静默死亡），但机制说错会误导排查方向 —— 真按"去查
> api.openai.com 的 401"去找，会浪费一轮。顺带说明为什么它格外难查：
> **模糊的连接错误比明确的配置错误更难定位**，这也是本节顺手让
> `get_embedder()` 在 base_url 为空时直接给出指名道姓报错的原因。（这一条在先前的导入阶段已经暴露过
并已补上 `https://ai.gitee.com/v1`，但**当时运行中的服务进程仍持有旧配置**。）

**第二个坑：重启服务时的配置缺口。** 修复 `.env` 后重启，`tools/list` 从 11 个工具变成
**0 个**，日志只有：

```
{"reason": "malformed", "event": "mcp_token_rejected"}
```

`malformed` 是个把"签名/过期/audience/issuer 全不过"揉成一个值的兜底原因，
**看不出是哪一项**。逐项核对后发现 `.env` 缺三项（且它们的默认值对本机拓扑全是错的）：

| 变量 | 默认值 | 本机应为 | 缺了会怎样 |
|---|---|---|---|
| `EMBEDDING_BASE_URL` | 回落 `api.openai.com` | `https://ai.gitee.com/v1` | dense 腿 401 → 纯 sparse |
| `OAUTH_ISSUER` | `http://localhost:8001` | `http://localhost:8002` | 去 8001 取 JWKS（404）+ iss 比对失败 |
| `PUBLIC_BASE_URL` | `http://localhost:8000` | `http://localhost:8001` | `aud` 应为 `…8001/mcp`，对不上 |
| `MCP_AUTHORIZATION_SERVERS` | `""`（空=不信任任何 AS） | `http://localhost:8002` | 信任列表为空，签名再对也判 `malformed` |

后三项是**两件独立的事**：`PUBLIC_BASE_URL` 是"我对外叫什么"，`MCP_AUTHORIZATION_SERVERS`
是"我信谁签的令牌"（`settings.authorization_servers` → `accepts_issuer`）。只配一个不够。

## 4. 第一步修复：补齐四项配置

`.env` 补上 §3 表格里的四项（见文件内注释；改动前已备份到 `/tmp/env.backup.*`），
重启 app 进程。这一步让 dense 腿复活。

## 5. 第二步修复：让降级到达调用方（契约）

只修配置是**不够的** —— 它修好了这一次，没修好这一类。补上降级信号本身。

改的是**契约**，不是行为：正常路径的返回一字未变，只有真的降级时才多出字段。

| 位置 | 改动 |
|---|---|
| `app/rag/retrieval/retriever.py` | 新增 `RetrievalDiagnostics`（`strategy` / `degraded_legs` / `notes` / `is_degraded`）与 `retrieve_with_diagnostics()`；原 `_hybrid` 主体移入 `_hybrid_with_diagnostics()` |
| `app/scenarios/hr_case_agent/read_executors.py` | `execute_search_policy` 改用新入口；降级时响应多出 `retrieval_degraded` 与 `retrieval_note`，并在 `summary` 前置`【注意】` |

三个刻意的设计决定：

1. **`_hybrid` 与 `retrieve` 的签名一个字没动。** 6 个既有测试与集成用例直接调
   `_hybrid`、5 处生产调用方调 `retrieve`；把诊断塞进它们的返回值会让调用方静默
   变成"解包两个值"。新增平行方法、旧方法做薄包装，是零破坏的改法。
   （两个"签名不变"的测试专门钉死这一点。）
2. **只有抛异常的腿才算降级，"正常返回空"不算。** sparse 对纯语义提问合法地 0 命中
   是常态；若把它也标成降级，标记会爬满正常回答，调用方很快学会无视它 ——
   等于把这次修复抵消掉。降级标记必须只在依赖真的坏了时出现。
3. **`outcome` 语义保持不变（仍是 `FOUND`）**：降级描述的是**排序质量**，不是
   "有没有依据"。把两者混进同一个枚举会改变 Agent 行为（可能把降级当失败而放弃
   作答），加正交字段才对。同理，没有降级时响应里**不出现**空数组字段 ——
   让"字段存在"本身就是信号。

## 6. 真正值得记的教训

`search_policy` 返回 `outcome: FOUND` + 一段自信的摘要，调用方（Agent / 人）
无从知道本次排序只用了关键词匹配。**这个缺陷的危险性不在"查不到"，而在"看起来很对"。** 降级路径本身是有意设计的
（dense 与 sparse 是独立两条腿，一条挂了不该拖垮另一条），文档字符串也写明
"降级必须**可见**"。问题是可见性只做到了**日志和 `/api/ready`**，
**没有做到工具响应契约**里：`search_policy` 返回 `outcome: FOUND` + 一段自信的摘要，
调用方（Agent / 人）无从知道本次排序只用了关键词匹配。

### `/api/ready` 的 `embedding` 到底是什么（重要澄清）

复盘时一度把 `embedding: unavailable` 读成"探测到 embedding 服务挂了"。**不是。**
`app/access/routes/health.py` 里它是一条**配置存在性**检查，不是可达性探测：

```python
# Embedding is a configuration fact rather than a reachability probe: there
# is no cheap "is the vendor up" call that does not spend tokens.
embedding_configured = bool(settings.embedding_base_url and settings.effective_embedding_api_key)
```

这条区别有实际后果，实测确认：

| 配置状态 | `/api/ready` 的 `embedding` | dense 腿 | 检索 |
|---|---|---|---|
| `EMBEDDING_BASE_URL` **缺失** | `unavailable` ✅ | 死 | 纯 sparse |
| URL **存在但不可达**（本次实测设为 `http://127.0.0.1:9/v1`） | **`ok`** ❌ | 死 | 纯 sparse |
| URL 正确 | `ok` | 活 | hybrid |

即：`/api/ready` 这次之所以能指路，是因为事故的成因恰好是**配置缺失**；如果成因是
"配了但连不通"，它会一边报 `ok` 一边静默降级。**它能证明"配了"，不能证明"能用"。**
这也是为什么修复必须落在响应契约上，而不是再加一条健康检查。
（对这条口径的处置见 §8.3。）

## 7. 验证

### 7.1 判定 dense 腿死活（§4 的修复）

干净的探针是**纯乱码 query**：Milvus 向量检索**没有分数阈值**，dense 腿活着就一定返回
top-k 近邻；dense 腿死了则整体为空。中文 query 做不到这一点 —— 两条腿都可能命中同一批
文档，看起来同样"合理"。

```bash
.venv/bin/python scripts/_probe_dense_leg.py
```

| 探针 | 修复前 | 修复后 |
|---|---|---|
| 乱码 `qzxwvbnm klprtgh`（sparse 必 0） | `outcome=FAILED`，0 条 | `outcome=FOUND`，3 条 → **dense 活着** |
| 英文 `What is the company policy on paid annual leave?` | 3 条全来自同一份用友模板（无意义） | 人社部实施办法 / 用友 / 国务院条例 → **跨语言语义检索生效** |
| 中文 `公司的年假是怎么规定的？` | 酒店考核表 #1 | **国务院令第514号 / 第五条 #1** |

### 7.2 降级是否到达调用方（§5 的修复）

单测：`tests/rag/test_retriever.py` +8、`tests/hr_case/test_read_executors.py` +2、
`tests/mcp/test_mcp_contract.py` +2；全量 **960 passed / 50 skipped**（改动前 948）。
其中一条专门从 **MCP 出口**断言 —— 只测工具函数返回不够，信封构造时按白名单挑字段
就会把标记丢掉，而那种丢失在工具层测试里完全看不出来。

端到端（真实 OAuth + 真实 HTTP，`eval-runner/policy_kb`）。故障态是把
`EMBEDDING_BASE_URL` 临时指向 `http://127.0.0.1:9/v1` 复现的（测完已还原，
`diff` 确认与测试前一致）：

| | 健康 | 人为制造故障（embedding 不可达） |
|---|---|---|
| `retrieval_degraded` | 不出现 | `["dense"]` |
| `retrieval_note` | 不出现 | 语义（向量）检索本次不可用，结果排序已退化为仅依赖剩余的一种检索方式…… |
| `summary` 前缀 | 直接是"命中 3 条制度片段" | `【注意】` + 上述原因 |
| `outcome` | `FOUND` | `FOUND`（不变） |
| 年假 query top-1 | 国务院令第514号 第五条 | 11_酒店工程部…技能考核表 ← **复现了原始错误**，但现在被明确标注 |

最后一行是这次修复的意义所在：**同一个错误答案，从"看起来像制度"变成"被标为不可信"。**

## 8. 第二步之后的延伸修复（同日完成）

§5 只解决了"字段到位"。字段到位 ≠ 模型会用 —— 没有一条指令告诉模型"看到降级该怎么办"，
它照旧会把排第一位的片段（当时是酒店技能考核表）当成定论。以下三件同日补齐。

### 8.1 上游提示词消费降级信号

| 位置 | 改动 |
|---|---|
| `retriever.py` | `RetrievalDiagnostics.prompt_directive()` —— 给**模型**的可执行指令，与给用户看的 `notes` 分开写 |
| `context_manager.build_policy_qa_messages` | 新增可选 `retrieval_notice`，追加到【任务】段 |
| `policy_qa/orchestrator.py` | 改用 `retrieve_with_diagnostics`；新增 `policy_qa_retrieval_degraded` 日志；两路 query 变体的诊断取**更差**的那份（`_worst_diagnostics`） |

三个刻意的选择：

1. **指令进【任务】段，不进证据块。** 证据块是 `UNTRUSTED_EVIDENCE`，混进去就等于把
   系统规则降级成"可以被'忽略以上'覆盖的素材"。有测试专门断言这一点。
2. **`notes` 与 `prompt_directive` 分开。** 前者说"为什么不准"（给人理解），
   后者说"因此必须怎么做"（给模型执行）。合并会得到一个既不像人话、又不构成指令的中间态。
3. **融合取更差**：两路只要有一路少了腿，"这条为什么排第一"就已不可靠；取最好会让
   降级在融合处被悄悄抹平 —— 那正是本类缺陷最初的样子。

**刻意不做**：不改 `confidence`。降级影响的是**排序**，不是证据的真实性；把置信度压到
阈值以下会让 `no_evidence_fallback` 丢掉真实引用，属于过度纠正。这是留给读者的判断题，
不是遗漏。

MCP 侧同步：`search_policy` 的工具描述里写明"返回带 `retrieval_degraded` 时必须说明排序
不可靠、请用户核对原文、不得把首位片段当定论"，`DESCRIPTIONS_VERSION` → `2026-09-16.1`
（评测基线据此对账）。

### 8.2 启动期配置一致性 fail-fast

`settings.validate_mcp_auth_can_accept_something` 在启动期拦住两种**自相矛盾**：

| 矛盾 | 触发 |
|---|---|
| 指了 AS 却不信任任何 issuer | `OAUTH_ISSUER` ≠ 默认值 且 `MCP_AUTHORIZATION_SERVERS` 为空 |
| 两种凭据都不可用 | 信任列表为空 且 `MCP_ACCEPTS_PLATFORM_TOKENS=false` |

第一条正是本机事故的形态。**刻意检查"矛盾"而不是"必须填"**：单端口部署、仅平台令牌
部署都是合法的，无脑要求非空会把它们一起打死。两条都带 `MCP_EXTERNAL_ENABLED` 出口。

### 8.3 `/api/ready` 的 `embedding` 口径澄清

**改为"加注"而非"改名"** —— 而且加注位置不是 payload。`tests/test_health_contract.py`
有一条硬不变量：每个 check **只能**有 `status` + `tier` 两个键（"public payload carries
status + tier only"）。往里加 `basis` 字段会破坏一个**刻意的**公开契约，所以改在：
模块 docstring + 端点 docstring（即 API 消费者读到的 OpenAPI 描述）明确写出
"配置存在性，不是可达性"；并用两条测试把语义**钉死**（配了但连不通 → 仍 `ok`；
没配 → `unavailable`），将来谁把它改成真探测，测试会失败并提示同步文档。

### 8.4 让"令牌被拒"的原因可诊断

**这一节推翻了本节原先的自荐方案。** 原计划是"启动日志里打印 `mcp_resource_url`"。
动手前先问了一句"这真的有用吗"，答案是没有：

- 它是**被动**信号：只在有人主动去比对时才有用，而配错 `PUBLIC_BASE_URL` 的人
  恰恰不会想到去比对 audience；
- 它**不阻止**任何事故，只是少读一次 settings；
- 最关键的：它传达不了那个必须知道的前提 —— "客户端申请的 aud 应该等于这个值"。

真正的病根在另一处，而且同一份代码文档里早就写了：

> 拒绝的原因要落在正确的类别上 —— 否则运维只能看到一堆「验证失败」，
> 分不清是配置错了、密钥轮换了、还是有人撤销了授权。
> —— `tests/mcp/test_as_token_verification.py` 开头的意图说明

文件确实为 `REVOKED` 记了 `as_token_revoked`、为注册缺失记了
`as_client_not_registered_locally`，**但 `MALFORMED` 这一族没有** ——
签名不过 / 过期 / audience 不符 / issuer 不在信任列表，四种原因共用一个值。
这不是新功能，是**与文件自身约定不一致**。改了两处：

| 位置 | 改动 |
|---|---|
| `resolve_access_claims` | 分流决策原本是静默的。新增 `as_token_issuer_not_trusted`：当令牌自称是 AS（http/https URL）却不在信任列表时记日志，带上 issuer 与**当前信任列表**，并在列表为空时点名 `MCP_AUTHORIZATION_SERVERS` |
| `_decode_signed_claims` | 新增 `as_token_decode_failed`：带上 `expected_audience` 与 python-jose 的原始原因（`detail`），让签名 / 过期 / audience 三者可分辨 |

两个刻意的约束：

1. **只进日志，不进响应。** 对客户端说清"为什么没通过"等于送攻击者一份免费的探测反馈 ——
   与模块开头"分流只用于选择验签路径、不构成信任"是同一条理由。返回给客户端的仍然是
   `TokenRejection.MALFORMED`，**响应契约一字未变**。
2. **不噪声化。** 平台自签令牌的 `iss` 是 `hrbp-ai-workbench`（不是 URL），它本来就走
   平台分支、本来就该静默。判别器 `_looks_like_an_authorization_server` 只认绝对
   http(s) URL，把平台流量排除在外。有一条测试专门守这个反向约束 —— 一个"到处都报警"
   的信号等于没有信号。

**实测（把 `PUBLIC_BASE_URL` 故意改成 `http://localhost:8000`）**：

```
改前： {"reason": "malformed", "event": "mcp_token_rejected"}
改后： {"event": "as_token_decode_failed", "detail": "Invalid audience",
       "expected_audience": "http://localhost:8000/mcp", "kid": "L4cUT8fd…"}
```

运维一眼即可判定"`PUBLIC_BASE_URL` 配错了，且当前解析成 8000"，不需要任何逆推。

这次实验顺带还清了一笔账：上一轮我**推断**过"`PUBLIC_BASE_URL` 默认 8000 会导致 aud
不匹配从而全量 401"，但**没有单独验证过**。现在验证了：客户端申请 `8001/mcp`、
服务端期望 `8000/mcp`，4 次请求全部被拒 —— 推断成立。测完已还原，`diff` 确认 `.env`
与测试前一致。

### 8.5 顺手修掉：单元测试在偷偷调外部 LLM

**这不是计划内的事，是被上面 §8.4 的验证过程撞出来的。** 全量套件连续两次跑到
SIGTERM 都没结束（`exit 137`），而半小时前同一套件只需 62 秒。

排查过程（值得记，因为它差点被误判）：

1. 用 `pytest -v` 重跑，卡点落在
   `test_policy_qa_kb_selection.py::test_citation_confidence_is_bounded_for_sparse_native_score`；
2. 但**单跑该测试 3.66 秒就通过** —— 说明是**间歇性**，不是确定性挂起，
   不能当成"偶发"忽略过去；
3. 直接查外部端点：`gitee_ai http=200 time=0.36s` —— 端点健康，
   所以不是"服务挂了"，而是"测试在等一个不该等的东西"；
4. 根因：`rewrite_query` 的 Step 2 会真的构造 `LLMOrchestrator` 并发起网络请求
   （`app/scenarios/policy_qa/preprocessors.py`）。而
   `test_policy_qa_kb_selection.py` 和 `test_stream_consistency.py` 的 orchestrator
   装配**只替换了 llm / retriever / guardrails，没有替换改写步骤** ——
   于是每个用例都打一次真实 LLM，延迟一抖整个测试就挂住。

**同一约定只在部分地方落实**：同一个文件里 `test_stream_omits_sources_event_…`
stub 了 `rewrite_query`，另外两个没有；`test_policy_qa_guard_order.py` 和
`test_indirect_injection.py` 全程都 stub。这是本轮反复出现的同一个形状
（§8.1 的"字段到位但没人告诉模型"、§8.4 的"拒绝原因只在部分位置记录"）。

修法：两个文件各加一个 **autouse** fixture stub 掉 `rewrite_query`。用 autouse 而不是
逐个补 monkeypatch，是为了让**以后新增的用例**默认就不带这个外部依赖。

**实测收益可直接量化**：

| | 修前 | 修后 |
|---|---|---|
| 全量套件 | 61.84s（且间歇挂死到 SIGTERM） | **33.81s** |
| `test_policy_qa_kb_selection.py` | 单跑 3.66s，抖动时 >60s | 1.05s |
| 合计 | 979 passed | **983 passed / 50 skipped** |

快了 28 秒，正是因为那 8 次真实 LLM 调用消失了 —— 无外网 CI 下同样的用例会直接挂。

### 8.6 同一症状的**第二次**发生：服务继承了随调用消失的临时代理

修完 §8.1–§8.5 之后，服务是以**脱离会话**的方式常驻的（`ppid=1`，见 §9.4），
启动当时端到端验证通过。几分钟后再问同一个问题，却又报出
`retrieval_degraded: ["dense"]`，且 top-1 又变回酒店技能考核表 ——
**与最初那次事故一模一样的症状，但原因完全不同。**

这次不必猜：可见性已经做到位了。`retrieval_leg_failed` 直接给出

```
leg        = dense
error_type = APIConnectionError
error      = Connection error.
```

`APIConnectionError` 说明是**连不上**向量化端点。而同一份代码在**当前的独立进程里
调用成功**（1024 维，0.98s）。差异只能在环境里：

| 探针 | 结果 |
|---|---|
| 服务进程持有的 `HTTPS_PROXY`（`127.0.0.1:51041`） | **connection refused** |
| 当前工具调用的 `HTTPS_PROXY`（`127.0.0.1:65448`） | 200 |
| 清除代理后直连 | **200** |

**根因**：运行环境注入了**每次调用临时生成本地代理**（端口随调用变化，调用结束即消失）。
通过工具调用启动的服务把它一并继承，于是出现最难受的时序形态 ——
**启动那一刻能出网，几分钟后开始连不上**；而 Postgres / Redis / Milvus 都走 localhost，
不受影响，所以 `/api/ready` 全程绿色。

这也解释了今天早些时候那个一直没想通的现象：用工具后台任务启动的服务为什么在
7 分 02 秒后被 `SIGTERM` 关闭 —— 它与注入代理同属**一次调用的临时环境**，
调用结束一起被回收。

**修复**（`scripts/start_local_app.sh`）：

1. 启动前 `unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy NO_PROXY no_proxy`，
   切断对调用方临时环境的依赖（本机直连实测可达，不需要代理）。
2. 新增**出网可达性自检**：只判"能不能建立连接"，任何 HTTP 状态码（含 404/502）都算可达，
   只有 `http_code=000` 才算不可达。
   注意**不要**拿 `/v1/models` 判健康 —— 实测它在 embedding 完全可用时也会返回 502。
3. 负向测试：把 `EMBEDDING_BASE_URL` 指向 `http://127.0.0.1:9/v1` → 拒绝启动并指明端点。

**写脚本时踩到的坑**：`echo "连不上 $PROBE_HOST（…"` 报 `unbound variable`。
`$PROBE_HOST` 后面紧跟**中文全角括号**时，bash 会把多字节字符的首字节并进变量名。
中文脚本里 `$VAR` 后面接中文必须写成 `${VAR}`。

**这一节的真正教训**（与 §6 那条并列）：这个缺陷的形状不是"配置错了"，
而是**服务的运行能力挂在一个只在启动瞬间存在的外部条件上**。
`/api/ready` 查不出它（依赖都健康）、配置校验也查不出它（配置确实没错）
—— 只有**启动时的连通性自检**能拦住它，因为那是唯一还能观察到"当时能连通"的时刻。



1. **`alg` 混淆尝试的告警**：`verify_as_access_token` 在 `header.alg != ES256` 时拒绝，
   但只返回 `MALFORMED`（与其他原因共用），没有留日志。这是一条**安全信号**
   （有人在做算法混淆攻击），值得单独记一条；本轮没做是因为它属于"新增检测能力"，
   与本轮"让既有拒绝可诊断"的目标不同类，不该顺手塞进来。
2. **CI 里的 DCR 限流**：`oauth_dynamic_registration_per_hour = 20` 是**进程内**滑动窗口
   （3600s），一个小时内跑够 20 次注册就会开始 429，且只能靠重启 AS 清零。
   本轮验证被它挡过一次，改用**复用既有已注册客户端**绕过。自动化冒烟若超过这个量级
   需要同样处理（或调用已存在的 `reset_registration_rate_limit()`，注释写明"测试用"）。
3. **`/api/ready` 的 `embedding`** 仍是配置检查（见 §8.3）。要让它证明"能用"需要一次
   真实调用（花 token），本轮选择的是"把口径写清"而非"换成更贵的探测"。
4. ~~把"服务进程由谁、以什么环境启动"记进 runbook。~~ **已做（2026-09-16）**：
   见 `scripts/start_local_app.sh`。本轮重启之所以把服务从"能查但排错"推到"全量 401"，
   正是因为原进程的环境变量来自 shell 而非 `.env`；`.env` 现已补齐四项。
   该脚本在**启动前**自检那四个变量（缺项直接拒绝启动并打印应填的值），
   而不是等第一个客户端来撞 401 —— 这是 §8.4 在 runbook 层面的收口。
   注意：本机 `macOS 无 setsid`，且用工具的后台任务方式启动的 uvicorn 会在该轮
   结束时被 `SIGTERM` 优雅关闭（实测 7m02s 后退出，日志为 `Shutting down` + session
   manager 关闭，不是崩溃）。要长驻必须脱离会话/进程组启动（`start_new_session=True`），
   判据是 `ppid=1`、且自身 `pgid == pid`。若哪天服务莫名消失，先按这条查。
