# Codex × Obsidian 长期项目记忆系统

**状态：** 已确认设计，待实施计划
**日期：** 2026-08-17
**Vault：** `D:\ObsidianVault`
**首个试点：** `D:\demo\hrbpilot`

## 1. 目标与边界

建立一个由用户拥有、可在 Obsidian 中直接阅读与修订的长期记忆系统，使 Codex 在代码项目任务中：

1. 开始任务前检索当前项目和跨项目的必要上下文；
2. 完成重要任务后沉淀经过筛选的长期知识；
3. 仅写入高价值、可验证且不含敏感数据的内容；
4. 不破坏 Vault 既有 PARA 结构、人工笔记或日记体系。

本系统不保存对话逐字稿、终端完整输出、临时尝试、密码、API Key、Token、Cookie、连接串、`.env` 内容或未经脱敏的业务/个人数据。

本系统不负责替代 Graft。Graft 保存当前仓库的可再生代码结构；Obsidian 保存跨任务、跨项目仍有价值的背景、决策、经验和状态。

## 2. 信息架构

保持现有 PARA 根目录不变，不创建平行的 `CodexProjects` 根目录。

```text
D:\ObsidianVault
├── 01Projects\02项目\<project-slug>\
│   ├── 项目概览.md
│   ├── 当前状态.md
│   ├── 技术决策.md
│   ├── 踩坑与失败方案.md
│   └── 变更记录.md
├── 02Areas\03开发与AI协作\
│   ├── 长期协作偏好.md
│   ├── 通用工程原则.md
│   └── 跨项目决策索引.md
└── 03Resources\03Codex\
    ├── 知识沉淀规范.md
    ├── 项目笔记模板.md
    ├── 任务提取规则.md
    ├── 敏感信息排除规则.md
    └── 待审阅.md
```

含义：

- `01Projects/02项目` 是活动代码项目的唯一归属；项目结束后整体移至 `04Archives`。
- `02Areas/03开发与AI协作` 存放长期有效的协作偏好和跨项目工程知识。
- `03Resources/03Codex` 存放系统规范、模板、规则和单一待审阅队列。
- `00PeriodicNotes`、现有 `daily/`、旧 `projects/` 与其他领域目录均不由自动化写入。

## 3. 项目识别和可写边界

每个项目以 `项目概览.md` 的 YAML frontmatter 作为唯一机器可读注册信息。自动化扫描 `01Projects/02项目/**/项目概览.md`，以规范化后的 `repo_root` 精确匹配当前 Git 根目录；不维护容易漂移的第二份注册表。

```markdown
---
type: codex-project
project_id: hrbpilot
status: active
repo_root: D:\demo\hrbpilot
tags:
  - project/hrbpilot
  - domain/hr
  - stack/python
last_codex_sync: 2026-08-17
---

# HRBPilot

<!-- codex:overview:start -->
<!-- codex:overview:end -->
```

所有由工具维护的内容必须位于命名的受控区块中：

```text
<!-- codex:<section>:start -->
<!-- codex:<section>:end -->
```

工具禁止修改受控区块以外的文字、frontmatter 中未定义的字段、日记和归档内容。受控区块丢失、重复或嵌套不合法时，工具必须拒绝写入、保留原文件，并输出可操作的修复错误。

## 4. CLI 契约

实现本地 CLI `codex-memory`。它是确定性读写层，不推断业务结论；Codex 负责给出任务语义和候选摘要。

```powershell
codex-memory register --repo <repo-root>
codex-memory context --repo <repo-root> --task <task-text>
codex-memory capture --repo <repo-root> --input <task-result.json>
codex-memory audit
```

### `register`

- 解析 Git 根目录，要求目录存在且可读；
- 创建五份项目笔记及最小 frontmatter；
- 仅在项目 `AGENTS.md` 的受控区块追加任务前读取/任务后沉淀规则；
- 不覆盖已有 `AGENTS.md`、项目笔记或 Vault 内容；
- 目标项目已注册时幂等退出；仓库路径冲突时失败并要求人工解决。

### `context`

- 精确定位项目，读取项目概览、当前状态、技术决策和踩坑笔记的受控区块；
- 根据任务文本、frontmatter 标签和项目标识检索有限数量的跨项目知识；
- 输出一个有明确 token 上限的 Markdown/JSON 上下文包，包含来源笔记链接；
- 不读取整个 Vault，不读取归档项目或无关日记；找不到项目时返回明确的 `not_registered`，不自动创建笔记。

### `capture`

- 输入为受 schema 校验的任务结果：任务摘要、修改范围、验证证据、候选决策/踩坑/变更/状态；
- 先执行敏感信息过滤、重要性判定、重复检测和受控区块校验；
- 将确定且有证据的内容写入对应笔记；不确定项写入单一 `待审阅.md`；低价值内容不写入；
- 使用临时文件 + 原子替换，写入前保留可恢复的同目录备份；
- 返回每项的动作（created / updated / queued / discarded / rejected）和理由。

### `audit`

- 检查活跃项目仓库路径、受控区块完整性、重复条目、过期下一步、已归档但仍 active 的项目；
- 只报告，不自动删除、移动或重写任何笔记；
- 输出 Markdown 和 JSON 两种机器/人工可读格式。

## 5. 任务生命周期

```text
开始项目任务
  → 确定 Git 根目录
  → codex-memory context
  → Codex 使用上下文 + Graft 理解当前代码
  → 实施、测试、验证
  → 判断任务重要性
  → codex-memory capture（仅重要任务）
  → 输出沉淀结果或失败原因
```

重要任务的触发条件为以下任一项：

- 改变架构、接口、数据模型、基础设施或关键依赖；
- 解决根因明确且可复用的故障；
- 完成独立功能并具有测试、构建或运行证据；
- 确认或推翻技术方案；
- 改变项目阶段、风险或下一步优先级。

普通问答、格式调整、临时命令、无结论排查、重复结论和未验证尝试不会写入长期记忆。

不使用文件监听器或定时扫描触发写入。任务完成事件由 Codex 工作流显式触发，避免中断任务、失败任务或未验证结论被误写入。

## 6. 记录模型与去重

正式条目包含稳定 ID、状态、日期、来源和证据。示例：

```markdown
### D-20260817-001：启动时基础设施采用非阻塞检查

- 状态：已确认
- 决策：Milvus / MinIO 暂时不可用时，FastAPI 不整体启动失败。
- 原因：存储层可惰性初始化；启动失败会扩大短暂基础设施波动的影响。
- 证据：`app/main.py::_ensure_infrastructure`；启动验证结果。
- 替代方案：启动时强制依赖可用。
- 影响：首次请求可能失败，但服务进程可恢复。
```

去重优先级：

1. 同项目、同条目类型、相同稳定 ID：更新现有条目；
2. 同项目、同类型、标题/核心结论相同：合并证据与最新状态；
3. 新结论推翻旧结论：旧条目标记 `已被替代` 并链接新条目，不删除历史；
4. 无法可靠匹配：进入待审阅队列，而不是猜测覆盖对象。

初版使用确定性规范化文本、条目 ID、标题和关键词匹配；不引入 embeddings、向量库或外部模型，避免额外成本和不可解释的合并。

## 7. 安全与可靠性

在模型判断之前、写入之前分别执行一次敏感信息检测。至少覆盖：

- `.env`、环境变量值、连接串；
- API Key、Bearer Token、JWT、私钥、Cookie、会话数据；
- 密码、电话、邮箱、身份证/地址等个人信息；
- 未脱敏的业务数据、完整请求头和完整日志。

检测到敏感字段时：删除可安全删除的字段并标记脱敏，或拒绝该条目；禁止将原始值写入待审阅队列、错误日志或 CLI 输出。

写入必须是幂等、原子和可恢复的：

- 同一输入重复执行不得产生重复条目；
- 写前验证所有目标文件，写入失败不得留下半写文件；
- 只创建可恢复备份，不自动清理历史备份；
- 没有 Vault 写权限、目标不存在或 schema 无效时立即失败并报告。

## 8. Codex 集成

集成分为两层：

1. 用户级 Codex 规则：在有 Git 仓库的任务开始前调用 `context`；重要任务完成后调用 `capture`；同步失败必须显式报告。
2. 项目级 `AGENTS.md` 受控区块：注册后保留相同规则，使仓库在独立打开时仍可使用对应 Obsidian 项目记忆。

实施前必须验证当前 Codex Desktop 对用户级规则、项目 `AGENTS.md` 和 hooks 的实际加载行为。若用户级“每个新任务”钩子不可靠，系统以项目 `AGENTS.md` + 显式 CLI 为确定性基线，不承诺不存在的平台事件能力。

## 9. 测试与验收

最小测试集必须覆盖：

- 注册一个空仓库、已有 `AGENTS.md` 的仓库、已注册仓库和路径冲突；
- `context` 的精确项目匹配、未注册项目、无关笔记排除和 token 上限；
- `capture` 的新增、更新、重复提交、替代旧决策、低价值丢弃、待审阅；
- 模拟 API Key、JWT、连接串、Cookie、邮箱和 `.env` 内容的过滤；
- 受控区块缺失/重复/损坏时拒绝写入；
- 原子写入故障注入，确保原文件可恢复；
- `audit` 对失效路径、重复条目和过期状态的只读报告。

验收完成标准：首个 `hrbpilot` 试点能在不改变 Vault 现有 PARA 导航和人工内容的前提下，稳定完成“检索上下文 → 执行任务 → 选择性沉淀 → 审计”。

## 10. 非目标

- 不将所有 Codex 对话自动归档到 Obsidian；
- 不创建数据库、云端同步服务、向量数据库或外部 LLM 依赖；
- 不自动提交 Git、更改 `.env`、迁移数据库或修改生产配置；
- 不自动删除、重命名或移动既有 Vault 内容；
- 不把 Graft 生成的代码图复制到 Obsidian。
