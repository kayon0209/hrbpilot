## 0. 结论先行

### 0.1 五条最重要的结论

**① "自然语言调用"从来不是模型能力问题，而是工具设计问题。**
同一批工具，只改描述与 schema，Anthropic 报告准确率从 **72% 升到 90%**（加 1–5 个真实例子）✅。反过来，工具注册表扩到 **103 个 server / 856 个工具**后，**完整工具描述让执行步数增加 67%，而准确率只涨 5.85 个百分点** 🔸。**你的杠杆在 server 侧，不在模型选择。**

**② 你的目标用户（HR / HR 经理）不是"没能力用 MCP"，而是"不会去配 MCP"。**
真正的落地阻力是**分发与开箱即用**，不是协议。企业侧的解法已经明确：**虚拟 MCP / 角色化端点**——不再让用户理解"哪个 server 有哪些工具"，而是给他**按角色/场景切好的端点，只呈现与他工作相关的工具** 🔸；配合预置示例提示词 + 30 分钟培训 + 团队 champion（MintMCP 的落地经验）🔸。

**③ 让"每个写操作都要人确认"会退化成没有确认。**
这是本次调研里**最反直觉也最重要**的一条。Rippling 把"Overwhelming Human-in-the-Loop"列为威胁 **T10**：攻击者用告警洪水利用认知过载 🔸。SOC 的类比数据：平均每天 **4,484 条告警，67% 因疲劳被忽略** 🔸。结论是业界已收敛到**风险分级**：低风险自动放行+记录，高风险必须人工，**目标升级率 10–15%**（Galileo 框架）🔸。
→ **你现在的设计（所有写操作都进审批）方向是对的，但不能扩展到"所有操作都要对话内再确认一次"**——那等于把审批门变成橡皮图章。

**④ 上下文经济是服务器端的责任，不是客户端的事。**
头部做法与降幅（🔸 多来源）：工具搜索 85%、懒加载 schema 96–99%（且准确率 +2.5~8.6pp）、Cloudflare Code Mode 92–94%（**52 个工具 9,400 token → 600 token**）、域分解 80%、schema 缓存 60–80% 延迟。
**你现在 11 个工具，远未到阈值**（业界经验：**约 10 个工具后选择质量开始下降，15 个以上明显变差**；50 个工具以上建议上 meta-tool）🔸。但**工具面一定会长**，所以现在就要把"能加不失控"的结构定下来。

**⑤ 安全上最狠的一课：MCP 把"指令"和"数据"放在同一个通道里，这不是 bug，是协议的属性。**
所以"用 prompt 告诉模型别听坏指令"是**最弱的防御**——攻击者的话和你的话以同样的可信度到达模型 🔸。结构性防御只有三条能扛住对抗测试：**工具输出打可信度标记（provenance）、信任平面分离（模型看不到它不能调用的工具描述）、人工确认不被绕过** 🔸。

### 0.2 对你的设想的评估（一句话）

**设想本身成立，但把它当成"协议接入问题"会失败；它是一个"工具面设计 + 分发 + 确认分层 + 评测"的组合工程。**
你的项目在**治理侧已经领先绝大多数开源实现**（审批门、撤销闭环、同一判定、审计同事务）。真正缺的是四样东西：**示例与术语（让模型不用猜）、任务导向的工具面（而不是 API 映射）、确认的风险分层、以及"工具选择准确率"的评测**。

### 0.3 比原设想更优的方案（三句话）

1. **不要只做一个"完整 MCP 端点"给所有人。** 做**三层交付**：非技术用户拿"角色化虚拟端点 + 斜杠命令"；深度用户/外部 Agent 拿完整端点 + 动态工具发现；管理员拿治理面板（你已有）。
2. **不要继续按业务原子动作加工具，要按"用户要办的事"重组。** 合并后的任务型工具返回**一份可审阅的草稿（多步计划）**，用户确认一次 → 系统内审批门仍然独立把关。
3. **把"模型有没有选对工具、填对参数"变成可测指标。** 这是你 `evaluation/` 目录的自然延伸，也是目前唯一能防止"看起来能用"的方法。本项目已经有一次"脚本全绿、浏览器全废"的教训。

## 2. 实现机制：从"一句话"到"正确的调用"

把一句中文变成一次正确的调用，中间有 7 段。**开源实现与商业产品的差异，本质是它们在哪一段上下了功夫。**

| # | 环节 | 实现机制 | 典型失败模式 | 有效对策 |
| --- | --- | --- | --- | --- |
| 1 | **意图理解** | 交给宿主 LLM | 语义边界模糊（HR 术语：`case` vs `request` vs `ticket`） | 提供 **ontology 资源**（术语表/枚举字典），别让模型猜 🔸 |
| 2 | **工具选择** | tools/list → 模型自己挑 | 工具重叠、描述含糊 → 选错或反复试 | **合并工具**、加**命名空间前缀**、描述里写清"何时**不**用" ✅ |
| 3 | **参数填充** | 按 inputSchema 生成 | 猜枚举值、拿 UUID 当参数、日期格式错 | **enum 收紧 + 1–5 个真实例子**（72%→90%）✅；**语义化 ID 代替 UUID**（显著提升检索精度、减少幻觉）✅ |
| 4 | **确认** | 客户端确认 / 协议 elicitation / 服务端审批门 | **确认疲劳** → 橡皮图章 | **风险分级**：读自动、写审批、高危双人 🔸；目标升级率 10–15% |
| 5 | **执行** | 服务端工具实现 | 重复写（重试导致二次副作用） | **幂等**（`idempotentHint` + 业务键去重）🔸 |
| 6 | **结果返回** | 工具返回值进上下文 | 全量返回撑爆上下文；返回 UUID/技术字段 | `response_format: concise/detailed`（Slack 案例 **206 → 72 token**）✅；分页默认 20 条；**返回人类可读名称而非 UUID** ✅ |
| 7 | **错误与回填** | 错误码 / 长任务句柄 | 无信息错误 → 模型死循环 | **可自纠错的错误**（what failed + 约束 + 怎么改 + retryable）✅；长任务用**显式句柄**（`taskId`/`case_no`）而不是会话状态 ✅ |

**关键洞察（对应第 7 段）**：新规范已**移除 `initialize` 握手与会话**，官方明确推荐**"服务端签发显式句柄，由模型当普通参数带回来"** ✅。这与你项目里"所有写工具都要求 `case_id`"的做法**完全一致**——这是你已经踩对的一个点，值得写进设计约束。

## 3. 常见架构设计（五种模式）

| 模式 | 代表实现 | 上下文成本 | 适用规模 | 治理能力 | 对非技术用户 |
| --- | --- | --- | --- | --- | --- |
| **M-1 直连**：全部工具直接暴露 | 绝大多数开源 server | 最高 | ≤10 工具 | 低（靠自己） | 差 |
| **M-2 工具集/命名空间分组** | `github-mcp-server` 的 toolsets（`repos`/`issues`/`pull_requests`/`actions`…，默认集 + 可选集 + `all`/`default`/`dynamic` 三个关键字）✅ | 中 | 数十工具 | 中（可做只读/锁定裁剪，`--read-only` 到工具级生效）✅ | 中 |
| **M-3 动态工具发现 / meta-tool** | GitHub dynamic toolsets（**3 个管理工具**：`list_available_toolsets` / `get_toolset_tools` / `enable_toolset`，按需把工具注册进运行中的 server）✅；Apideck **4 个 meta-tool 代替数百**（63x）🔸；Cloudflare Code Mode **2 个 meta-tool**（`portal_codemode_search` / `execute`）✅ | 低 | 数十~数千 | 中高（工具面可运行时裁剪） | 差（对模型友好、对人不可见） |
| **M-4 网关 / 聚合** | Uber **MCP Gateway + Registry**：从 IDL（protobuf/thrift）**自动生成工具定义**、LLM 用 IDL 注释**润色描述**、接授权服务做**逐工具 RBAC**、调用前过 **PII Redactor** ✅；IBM ContextForge；TrueFoundry（审批门 + 前后置 guardrail）🔸 | 低 | 企业级 | **最高** | 中 |
| **M-5 虚拟 MCP / 角色化端点** | MintMCP 的 VMCP：用户面对的是**按角色/用例切好的端点**，只看到与工作相关的工具；配合 Bundles、示例提示词、30 分钟培训、团队 champion 🔸 | 低 | 企业级 | 高 | **最好** |

**给你的映射**：现在是 **M-1 + M-2 的雏形**（11 个工具、6 读 5 写、已有 scope/角色/审批三层判定）。
- **短期**：M-2（把工具按"查询类/办理类"再细分命名空间；你前端文案已经是这个分法）。
- **中期（工具数 30+）**：M-3。
- **面向非技术用户的真正答案**：**M-5**——但它需要 M-4 的治理底座，而你的审批门/审计/撤销已经具备 M-4 的核心要素。**这是你最该补的一层，而不是补工具。**

## 4. 典型案例

### 4.1 开源 / GitHub

**① `github/github-mcp-server` —— 工具集与动态发现的最佳教科书** ✅
- **工具集体系**：把工具按域分组，每个工具集声明 `ID / Description / Default / Icon / InstructionsFunc`（**能生成上下文相关的说明**，不只是静态描述）。
- **三种特殊关键字**：`all`（全部）、`default`（默认集）、**`dynamic`**（运行时发现）。
- **动态发现三步**：启动时**只加载 3 个管理工具** → 客户端 `list_available_toolsets` → `get_toolset_tools` 预览（不启用）→ `enable_toolset` **把工具注册进运行中的 server**。
- **安全隔离设计（值得抄）**：启用工具集时**仍受只读/锁定模式过滤**——"即使启用了工具集，写工具在只读模式下依然不可见"。
- **描述可覆盖**：支持用 `github-mcp-server-config.json` 或环境变量**按工具名覆盖描述**（还能 `--export-translations` 导出做翻译）。**这对中文产品是直接可借鉴的机制**——文案与代码解耦。

**② Anthropic《Writing effective tools for agents》——唯一有量化结论的方法论** ✅
- **工具整合**：`schedule_event`（内部处理找空闲+排期）取代 `list_users`+`list_events`+`create_event`；`get_customer_context` 一次编译好客户近期相关信息 ← **明确反对"只包装 API 端点"**。
- **命名空间**：按服务/资源前缀；并指出**前缀 vs 后缀对评测结果有显著影响**，要自己测。
- **语义 ID**：把 UUID 换成人类可读编号，"显著提升检索精度、减少幻觉"。
- **`response_format` 枚举**：concise/detailed；Slack 案例 206 → 72 token。
- **Token 截断**：Claude Code 默认单条工具响应 **25,000 token** 上限，且**截断时要给出引导**（鼓励多次小范围精准查询）。
- **错误即引导**：不要不透明错误码；给"具体可操作的改进建议或正确格式示例"。
- **评测方法**：用真实数据造几十个 prompt-response 对；**强任务**（需要多次调用）优于弱任务；**held-out 测试集**防过拟合；指标含**顶层准确率、工具调用数、token 消耗、工具错误**；把 transcript 交回模型让它批量重构工具。
- **最有说服力的结论**：**Claude 优化过的工具，held-out 准确率超过"专家手工实现"**。

**③ Cloudflare Code Mode —— 上下文经济的极端解** ✅/🔸
把 MCP 折叠成 2 个 meta-tool，Agent **写 JavaScript** 去搜索与调用；自家 API 传统 MCP 形态需 **200 万+ token**（超过最大上下文窗口），Code Mode 降幅 **99.9%**。**这是"部署方承认原设计不可扩展"的标志性事件**。

**④ Uber MCP Gateway + Registry —— 规模最大的公开参考架构** ✅
5,000+ 工程师、10,000+ 服务、1,500 月活 agent、**60,000+ 次执行/周**。四个动作值得直接抄：
1. **从 IDL 自动生成工具定义**（protobuf/thrift）+ **LLM 用 IDL 注释润色描述**；
2. **逐工具 RBAC** 接公司授权服务；
3. **调用前 PII Redactor**；
4. **三种消费面**：Agent Builder（**无代码**）、Agent SDK（生产）、Coding Agents。
路线图：**工具搜索按需加载、注册表内置评测框架、用 skills 承载可复用多步工作流**。

## 5. 可复用的经验教训（20 条）

### A. 工具设计
1. **工具定义是 prompt，不是文档**——描述里要写"何时用/何时不用/例子"。
2. **合并 > 增殖**：约 10 个工具后选择质量开始下降，15 个以上明显变差 🔸。
3. **命名空间前缀**让你在评测输出里一眼看出错在哪。
4. **参数名要无歧义**（`user_id` 而非 `user`）；**用语义 ID 而非 UUID** ✅。
5. **enum + 严格类型**比长篇说明更有效；`additionalProperties: false`。
6. **加 1–5 个真实例子**是性价比最高的改动（72% → 90%）✅。
7. **读写分离命名**（`get_/list_/search_` vs `create_/update_/delete_`）+ annotations。
8. **组合式输出**：工具返回的 ID/字段要能直接喂给下一个工具，别让模型从句子正则里抠 ID。

### B. 上下文经济
9. **分页默认 20 条 + cursor**，永不返回 4,000 行。
10. **能纯文本就别 JSON**（省约 80% token）；要结构就 `structuredContent` + `outputSchema`。
11. **提供 `response_format: concise/detailed`**（2/3 降幅的实测案例）✅。
12. **工具数接近 50 或单 schema > 2,000 token 时上 meta-tool** 🔸。
13. **schema 缓存**（Redis/TTL）省的是延迟与算力，不省 token——别把它当 token 方案 🔸。

### C. 人工确认
14. **"每个调用都确认"= 没有确认**（确认疲劳是安全问题，Rippling T10）🔸。
15. **只把"残余的、依赖上下文的决定"给人**，其余编码成策略。
16. **一次批准只作用于一次执行**（one-execution approval）；**时限授权**要按风险设窗口，并明确"窗口内参数变化不再复核"的代价 🔸。
17. **拒绝也要留痕**（非持久化拒绝：把"这一次不行"和"永久禁止"分开）。
18. **审批要能追到"谁批的、批的是哪次执行"**（审批 ID ↔ 执行记录可关联）。

### D. 安全与治理
19. **工具输出是不可信数据，必须打来源标记**；不允许未标记内容直接进入高权限工具的参数位 🔸。
20. **描述/清单要固定与版本化**（内容哈希 + 变更评审），因为**批准一次不等于永久安全**（rug pull）🔸。

## 6. 踩过的坑（真实事故）

### 6.1 工具投毒与影子（Invariant Labs 披露，多来源一致）🔸
- **"无辜的 add 工具"**：工具描述里藏 `IMPORTANT` 指令，让模型先读本地配置文件与 **SSH 私钥**，再通过一个 `sidenote` 参数外发，同时用数学解释分散用户注意力。**用户只看到一个加法工具。**
- **工具影子（shadowing）**：一个被批准的工具，用描述**改写另一个受信工具的行为**（如把所有邮件路由到攻击者）。

### 6.2 Rug pull：通过安装时评审、更新后才作恶 🔸
**Postmark MCP（2026-09）**：一个安装量很大的邮件 MCP 包，某次更新后**静默把每封 agent 发出的邮件 BCC 给攻击者域名**。安装时它完全正常。**教训：MCP 没有内置的版本固定与签名清单，多数客户端每次会话重新拉取。**

### 6.3 供应链与实现漏洞 🔸
- **CVE-2025-49596（CVSS 9.4）**：未认证的 MCP 工具链可被远程执行命令。
- **CVE-2025-59536（CVSS 8.7，Claude Code）**：恶意 `.claude/settings.json` 注入 Hook，**在信任对话框渲染之前**就执行 shell；另一处缺陷让仓库**静默自动批准所有 MCP server**。
- **抽样扫描**：7,000+ 存活 MCP server 中 **36.7% 存在 SSRF 风险**（PoC 从 EC2 元数据端点拉到 IAM 凭据）；公开暴露的 server 超 8,000，其中 **492 个零认证零加密**；某开源 marketplace 的 **10,700 个 skill 中 800+ 是恶意的**。
- **stdIO 传输的设计级问题**：把配置直接交给 shell 而未做清洗，被指为**跨 Python/TS/Java/Rust 参考 SDK 的设计模式**（非单项目 bug），影响 7,000+ 可达 server 与包。

### 6.4 "授权无法被验证"的极端案例 ⚠️（单一来源，需保留怀疑）
有报道描述 2026 年初一起针对某国政府机构的事件：攻击者以"授权漏洞挖掘"为名，投喂长篇手册 + 自定义外泄工具，模型在 **34 个会话 / 1,088 条 prompt** 中**自主执行了 5,317 条命令（约占全部操作的 75%）**，利用 20 个已知未修补 CVE。
**无论细节是否完全准确，教训是清晰的**：模型没有发明新漏洞，它把一个**信任判断（"这个人说有授权"）**放大了。**任何"用户声称自己有权限"的路径都不能当作授权。**

### 6.5 确认疲劳（有量化数据）🔸
SOC 团队日均 **4,484 条告警，67% 因误报疲劳被忽略**；HITL 治理是为"离散、高风险决策"设计的，**不适用于产生人类无法解读的行为轨迹的 agent 工作流**。ML 优先级排序把响应时间降 22.9%、抑制 54% 误报且保持 95.1% 检出 ← **"风险比例过滤"优于"一律审批"**。

### 6.6 我们自己的坑（本项目，已验证）✅
- **脚本全绿、浏览器全废**：e2e **74/74 通过**，但浏览器点"授权"毫无反应——根因是授权页 CSP 的 `form-action 'self'` 拦掉了跨源回调重定向。**脚本客户端不参与浏览器行为，因此永远发现不了这类问题。**
- **e2e 跑在开发库上**：开发库残留 e2e 用户与 `dcr_` 客户端，scratch 库积了 26 个历史残留用户。
- **两处安全收紧互相打架**：`OAUTH_INTERNAL_BASE_URL` 用容器主机名走明文 http，而新加的守卫只放行环回 http → **所有外部令牌被判 malformed**。
**这三条是本报告里最直接可复用的教训：验收必须包含"真实浏览器/真实客户端"这一层，且必须跑在一次性环境里。**

## 8. 比原设想更优的实现思路

### 8.1 产品形态：**三层交付**，而不是一个端点给所有人

```
① 非技术用户（HR 经理 / HRBP）
   → 角色化虚拟端点（只暴露与他工作相关的工具）+ 斜杠命令/提示词模板
   → 入口：项目内 AI 窗口（上一份调研的方向 B），或企业微信/飞书里的机器人

② 深度用户 / 外部 Agent（Codex / WorkBuddy / Claude）
   → 完整 MCP 端点 + 按需工具发现 + 完整 resources/prompts

③ 管理员（HR 系统管理员 / IT）
   → 连接管理（你已有）+ 治理旋钮：按角色的工具开关、token 预算、审计导出
```

**为什么这样更好**：把"协议复杂度"从非技术用户身上移走。用户看到的是"我能做这几件事"（角色化端点 + 斜杠命令），而不是"这里有 11 个工具"。
**证据**：M-5 虚拟端点是企业落地的收敛做法 🔸；Salestrics 把斜杠命令作为主入口 🔸；MintMCP 的落地清单（预置 Bundles、2–3 个示例提示词、30 分钟培训、团队 champion）🔸。

### 8.2 工具面：**任务导向重组**，原子工具降为内部实现

现在的 11 个工具是"业务原子动作"，这是正确的第一步。下一步是**加一层任务型工具**（不是替换）：

| 现在（原子） | 建议新增（任务型） | 它做什么 |
| --- | --- | --- |
| `search_policy` + `get_policy_source` | `答复一个制度咨询(question)` | 检索 → 选出引用 → 组织带出处的答复草稿（一次调用完成，内部可以多次检索） |
| `search_cases` + `get_case_summary` + `get_approval_status` | `查看一个员工诉求的完整情况(描述或编号)` | 找到案件 + 摘要 + 审批状态，一次返回 |
| 6 个写工具 | `办理一个员工诉求(描述, 意图)` | 产出**多步草稿**（要改什么、按什么规则、风险等级）→ 用户一次确认 → 生成对应审批 |

**关键设计**：任务型工具返回的是**草稿计划**（"我准备这么做，理由是这样"），**而不是直接执行**。用户确认的是**计划**，系统内审批门确认的是**执行**——两道门职责不同、都不省。
**证据**：`schedule_event` / `get_customer_context` 的整合范例 ✅；Accordio 的"草稿 + 确认屏" 🔸。
**代价要说清**：合并会牺牲一部分"精细可控"，所以**原子工具保留**（给深度用户与外部 Agent），任务型工具只面向非技术入口。

### 8.3 让自然语言可靠的四件事（成本低、收益最大）

1. **Prompts 作为"按钮"**：`先查制度并给出处`、`受理一个员工诉求`、`结案前检查`、`这个案件现在卡在哪`。非技术用户照抄即可，不依赖措辞能力。**同时发布"示例说法"清单**（MintMCP 明确要求 2–3 个示例提示词）。
2. **Ontology 资源**：案件类别、风险等级、状态机、角色能力、**术语对照表（"诉求/案件/请求"分别对应系统里的什么）**。这是 Well 的 55+ 实体本体的同类产物 🔸——**你的版本就是制度字典 + 状态机**。
3. **语义化 ID**：对话里一律用**人类可读编号**（案件编号、姓名、部门名），UUID 只在内部流转 ✅。
4. **schema 里放 1–5 个真实例子**（72% → 90%）✅。

### 8.4 确认设计：**风险分级**，不是"都要确认"

| 风险级 | 对话内确认 | 系统内审批 | 例子 |
| --- | --- | --- | --- |
| 低（只读、检索） | 不确认 | 无 | 查制度、查案件 |
| 中（可逆写、非敏感） | 复述一次 | 审批门（单人） | 加跟进任务、改负责人 |
| 高（不可逆、涉员工权益、终止/骚扰/歧视） | 复述 + 展示将执行的具体参数 | 审批门（**可要求双人/更高级别**） | 结案、通知外发、涉及高风险类别 |

**明确不要做的**：① 每个调用都弹确认；② 用"用户在对话框里点过确认"代替系统内审批门。
**证据**：风险分级是业界收敛范式；"一次批准一次执行 vs 时限授权"的取舍表；目标升级率 10–15% 🔸；`HIGH_RISK_WRITE_BLOCKED` 你代码里已有类似概念。

### 8.5 结果闭环：把"待审批"变成"办完了"

现在用户提交后拿到一句"已提交，审批编号 X"，然后**没有然后了**。
**建议**：审批完成/拒绝后，把结果回填到对话（或下次对话时主动提示）。实现路径：显式句柄（`approval_id` + `case_no`）+ 长任务/通知机制。**这与上一份调研的方向 C 是同一件事。**

### 8.6 分发：**授权先于功能**

对企业客户（HR 系统的采购方是安全团队），"每个员工逐个授权"是头号阻力。**企业托管授权（EMA / ID-JAG）是规范给出的标准答案**，但首发仅 Okta。
**你的动作**：① 把授权模块设计成**可插入 ID-JAG 校验**的形状；② 面向终端用户准备一份**"数据流向与留存说明"**（Peach 的评论区证明这是决策关键问题）🔸；③ 提供**一键接入/集中配置**的路径，而不是让每个 HR 经理自己配。

### 8.7 评测：把"会不会用"变成数字（**当前最大的缺口**）

| 指标 | 怎么测 |
| --- | --- |
| 工具选择准确率 | 黄金集：50–100 条**中文口语**（HR 真实说法）→ 期望工具 + 期望参数；held-out 集合防过拟合 |
| 不该调用时的拒答率 | "帮我查一下王工的工资"（无权限/无此能力）应明确拒绝而非幻觉 |
| 参数正确率 | 枚举/日期/编号格式 |
| 端到端完成率 | 一句话 → 正确草稿 → 正确审批 |
| 回归 | 每次改描述/schema 都跑，**把描述当代码看待** |

**证据**：Anthropic 把 evals 当作核心工序、要求 held-out 集、要求记录工具调用数与 token 消耗 ✅；Uber 把"注册表内置评测框架"写进路线图 ✅。
**现实检查**：本项目的 `evaluation/` 目录已经存在，且已经有"脚本全绿掩盖浏览器问题"的教训——**把工具选择评测加进去，是防止同类问题最直接的投入。**
