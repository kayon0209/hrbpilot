# ADR-0001：单一受控 HR Case Agent，而非 Multi-Agent

> 状态：已接受 · 日期：2026-08-28 · 关联：HRBPilot 升级计划 Phase 5–7

## 背景

升级计划明确禁止把所有节点/步骤包装成 "Multi-Agent"。HR Case 场景需要一个能分类、检索、建单、通知、跟踪状态的执行体，需要在「能力」与「可控性」之间做架构选择。

## 决策

采用**单一受控 Agent**：一个有界的执行循环（`agent_loop.run_plan`）+ 服务器端强制的状态机（`state.py`）+ 工具白名单（`tools.py`）+ 人工审批门（`ApprovalRequest`）。LLM 只产出符合 Schema 的计划（`Planner.validate` 服务器端重验证），永远不直接触碰数据库或 HTTP 客户端。

## 理由

1. **可审计性**：单循环、单计划、单审批链，`case_events` 的 seq 天然完整；多 Agent 的协商过程无法用 append-only 事件完整重建。
2. **安全边界清晰**：写工具的执行必须穿过 `begin_tool_execution` 的四重检查（审批状态 / 过期 / 参数哈希一致 / 未消费）；多 Agent 需要把这条链复制到每个协作方，或引入跨 Agent 信任问题。
3. **评测可重复**：Phase 6 的轨迹评测依赖「同样输入 → 同样轨迹属性」；多 Agent 的动态分派会引入不可复现的路径。
4. **现有场景不受影响**：五个场景编排器保持独立；HR Case Agent 是新增的有界执行体，不是对它们的重写。

## 后果

- 正面：未授权写 = 0、重复副作用 = 0 可用单元测试直接锁死；run 轨迹（`GET /{case_id}/runs/{run_id}`）可完整回放。
- 负面/代价：需要跨步骤的复杂研究类任务目前不在此架构的能力范围内；若未来需要，应以「新的受控 Agent」扩展，而非把本 Agent 拆成多个协作方。

## 备选方案（否决原因）

- LangGraph 持久化图运行时：现有实现是清晰可测的状态机，尚无持久化图运行时的实际需求，为关键词引入框架违反最小代码原则。
- 多 Agent 协作（planner/worker/critic 分体）：审计链被协商过程打断，审批边界模糊，评测爆炸。
